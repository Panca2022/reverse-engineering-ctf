# Encrypted Message — CTF Writeup

## Summary
An unstripped Linux ELF binary hides a secret "license key." Submit the
correct key to reveal a `flag{...}` containing 20 random alphanumeric
characters. The flag changes on every run.

**Difficulty:** Easy–Medium
**Category:** Reverse Engineering
**Skills tested:** `file` identification, `strings`, symbol table reading,
`objdump`, x86-64 little-endian decoding, XOR reasoning.

---

## Step 1 — Identify the binary

    $ file challenge_binary
    challenge_binary: ELF 64-bit LSB pie executable, x86-64,
      dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
      BuildID[sha1]=e652f09618dd01e5cb009118fa1b6ffab9ae8cc9,
      for GNU/Linux 3.2.0, not stripped

**Key fact:** `not stripped`. The symbol table is intact, so function
and global names survive in the binary.

---

## Step 2 — Extract strings

    $ tr -c '[:print:]' '\n' < challenge_binary | grep -iE "flag|secret|denied|enter"
    Zflag{
    Enter License Key:
    Access Denied! Wrong code.
    Hey! You found the flag: %s

`Zflag{` is the encrypted form of `flag{`. A single-byte XOR is the
likely obfuscation — but we will not need to attack it directly.

---

## Step 3 — Read the symbol table

    $ readelf -s challenge_binary | grep -E "xor_key|xor_encrypt|main|generate_random|charset"
        21: 0000000000002020    63 OBJECT  GLOBAL DEFAULT   16 charset
        35: 0000000000001226    76 FUNC    GLOBAL DEFAULT   14 xor_encrypt
        39: 0000000000001272   359 FUNC    GLOBAL DEFAULT   14 main
        40: 000000000000205f     1 OBJECT  GLOBAL DEFAULT   16 xor_key
        43: 00000000000011a9   125 FUNC    GLOBAL DEFAULT   14 generate_random

The function names tell the entire architecture:
- `xor_encrypt` — the obfuscation function
- `xor_key` — a global key variable
- `generate_random` — builds the flag characters
- `charset` — the pool of characters

---

## Step 4 — Disassemble `main`

    $ objdump -d -M intel challenge_binary > disasm.txt
    $ sed -n '/<main>:/,/^$/p' disasm.txt

Relevant fragment:

    127d: movabs rax, 0x50324b4d38465443
    1287: mov    QWORD PTR [rbp-0x8f], rax
    128e: movabs rax, 0x00585a5639514c50
    1298: mov    QWORD PTR [rbp-0x88], rax
    ...
    12ae: call   xor_encrypt          ; first XOR pass
    ...
    1353: call   xor_encrypt          ; second XOR pass
    ...
    1398: call   strcmp               ; compare user input with decoded buffer
    139d: test   eax, eax
    139f: je     13b7                 ; equal → success

Two observations:

1. The two `movabs` instructions write to **overlapping stack
   addresses** — the second store overwrites the first's last byte
   with an identical byte. The result is one `P`, not two.
2. `xor_encrypt` is called twice on the same buffer. XOR is its own
   inverse, so the net effect is identity — the obfuscation buys nothing.

---

## Step 5 — Recover the secret code

Decode the little-endian QWORDs byte by byte:

**First value** `0x50324b4d38465443`
→ bytes `43 54 46 38 4d 4b 32 50` → ASCII **`CTF8MK2P`**

**Second value** `0x00585a5639514c50`
→ bytes `50 4c 51 39 56 5a 58 00` → ASCII **`PLQ9VZX\0`**

Because the second store starts at `rbp-0x88` (the address the first
store used for its last byte), the byte `'P'` at `rbp-0x88` is written
twice. Both writes are `'P'`, so the final memory contents are:

    rbp-0x8f:  C  T  F  8  M  K  2  P  L  Q  9  V  Z  X  00

**Secret code: `CTF8MK2PLQ9VZX`** (14 characters)

---

## Step 6 — Get the flag

    $ echo "CTF8MK2PLQ9VZX" | ./challenge_binary
    Enter License Key: Hey! You found the flag: flag{9yMpiaicoY14BgBMA6ax}

The 20-character payload is generated by `generate_random` and seeded
with `srand(time(NULL))`, so every run produces a different flag.

---

## Defensive lessons

1. **Always strip production binaries.** The symbols gave away the
   whole design before any code was analysed.
2. **XOR is not encryption.** Double XOR is a no-op.
3. **Compiler string handling is not a secret.** Short strings end up
   as immediate `movabs` instructions in the instruction stream,
   trivially readable from the disassembly.
4. **Obfuscation raises cost; it does not provide confidentiality.**
